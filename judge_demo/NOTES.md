# 判题器笔记（设计与进展）

> 记录核心设计决策与实测结论，可直接用作实验报告素材。

## 当前能力

```
./judge <源文件> <数据目录>
```

六个判定全通：CE / AC / WA / TLE / RE / MLE，支持多测试点。

```
$ ./judge test.cpp testdata
compile ok
Test 1
run done
peak memory: 3584 KB
AC
Test 2
run done
peak memory: 3584 KB
AC
Test 3
run done
peak memory: 3584 KB
AC
all 3 test passed
```

退出码对照表：

| 情况 | 退出码 | 说明 |
| --- | --- | --- |
| 全部测试点通过 | 0 | |
| 某个测试点 WA / TLE / RE / MLE | 1 | 立刻停止，不再跑后面的测试点 |
| 编译失败（CE） | 1 | |
| 数据目录里没有数据 | 1 | 一组都没测，不算通过 |

## 整体结构

```
main
 ├── compile(源文件)                  编译一次
 └── run_one_test(输入, 答案) × N     逐组跑（N 由数据文件决定）

compile 内部：      fork + exec g++ / pipe + dup2(→2) / read 报错判 CE
run_one_test 内部：fork + exec ./test / open + dup2(→0, 1)
                   setrlimit 保命 → alarm 限时 → 判 TLE / MLE / RE / AC / WA
```

## 关键设计决策

### 1. 抓 g++ 报错（pipe + dup2）

- 子进程：close(fd[0]) → dup2(fd[1], 2) → close(fd[1]) → exec g++
- 父进程：先 close(fd[1])，再 read 到 EOF
- **父进程必须先 close(fd[1])**：不关的话 read 永远等不到 EOF，程序卡死（已实测）
- **read 必须写在 waitpid 之前**：否则报错超过管道容量（约 64KB）时双向死锁
- read 会"短读"，所以要 while 循环；缓冲区留一格给结束符，用 sizeof(buf) - 1

### 2. 喂输入 / 收输出（open + dup2）

- 子进程：open 输入（只读）与输出（写入 + 创建 + 清空），再 dup2 到 0 号和 1 号
- 用文件而不用管道：避免 64KB 死锁；天然对接比对逻辑；调试时可直接 cat output.txt

### 3. 超时（alarm + 信号）

- alarm 只有一处位置正确：**子进程里、exec 之前**
- fork **不继承**闹钟（实测：父进程 alarm(2) 到点被杀，子进程活满 5 秒）
- exec **保留**闹钟（实测：exec 成 sleep(10) 的程序，1.003 秒被 SIGALRM 杀死）
- 每组数据都有独立的 2 秒超时：每轮 fork 出来的子进程都是全新的，闹钟自然重新计时

### 4. 判定"被信号杀死"

- WIFEXITED 为真 → 正常退出，用 WEXITSTATUS 取退出码
- WIFSIGNALED 为真 → 被信号杀死，用 WTERMSIG 取信号号
- SIGALRM(14) → TLE；SIGSEGV(11) → RE
- 注意：WIFEXITED 为假时，WEXITSTATUS 取出的值毫无意义

### 5. 比对

- 逐行读，每行末尾补换行再拼接
- **不能丢行边界**：否则输出 "3\n0" 与答案 "30" 会被判成相等，误判 AC
- 对判题器来说，"误判 AC" 远比 "误判 WA" 严重（错的被当成对的，没人会发现）

### 6. 多测试点：怎么知道一共有几组

- 文件名按规则拼出来：`目录 + "/" + to_string(i) + ".in"`、`.ans`
  - i 从 **1** 开始 —— 数据文件叫 `1.in`，不叫 `0.in`（差一错误）
  - `open()` 只认 `char*`，`std::string` 要 `.c_str()` 转过去
- 循环写成 `for (int i = 1; ; i++)`：中间**留空** = 条件恒真 = 永不主动停，只能靠 `break` 出来
- 停止信号 = **探路石**：

```cpp
ifstream check(ans_path);
if (!check.is_open()) break;
```

- **判题器不该知道有几组数据**，只该"一组一组往下走，走到没有为止"——出题人加一组数据，不用改代码
- **探路必须在父进程做、在 fork 之前**：
  - 需要"知道没有下一组了"的是循环，而循环在父进程里，`break` 也只能在父进程写
  - 若交给子进程 `open` 失败后 `return 1` 报信 → 与用户程序自己的 `return 1` 撞车，退出码分不清
  - 且此时 `output.txt` 已被清空、报错已打到终端，副作用无法挽回
- `cout << "Test " << i` 必须放在探路**之后**，否则会多印一组空头支票（实测踩过：印了 `Test 4` 却什么都没跑）
  - 与"read 必须在 waitpid 之前"同类：**语句顺序本身就是逻辑**

### 7. 结论靠退出码

- 判题器对整个系统的唯一输出是**退出码**：0 = 通过，非 0 = 不通过
- 屏幕上打印的 AC/WA 是给**人**看的，退出码是给**程序**看的（将来 Web 后台只读退出码）
- WA 时用 `return 1` 而**不是 `break`**：`break` 只跳出循环，程序继续往下走，退出码仍是 0 —— 失败信息就丢了
- 空数据保护：`int passed` 计数器（**必须声明在 for 外面**），循环后 `if (passed == 0) return 1`
- **实测踩过的四个"假通过"**，都是"编译不报错、程序不崩、安静地说谎"：
  1. 循环里两轮读的还是同一个文件 → 假 AC（把 2.ans 改成 999 仍报 AC 才暴露）
  2. WA 却没 `return 1` → 屏幕印 WA，**退出码却是 0**
  3. 数据目录空 → 打印正常结束，**退出码 0**
  4. 拆函数时漏掉 `compile()` 调用 → 拿**上一轮遗留的 `test` 二进制**去跑 → 假 AC（详见第 10 节）

### 8. 内存限制：两个数字，两个用途

**两套独立机制，各管各的：**

| | 数字 | 限制的是什么 | 用途 |
| --- | --- | --- | --- |
| `setrlimit(RLIMIT_AS, ...)` | 宽松（演示用 1GB） | **地址空间** | **保命** —— 挡住 `new char[1TB]` 这类炸弹 |
| `ru_maxrss` 与题目限制比较 | 256MB | **物理内存峰值（RSS）** | **判分** —— 准确说出"你超了" |

- **笼子不能设成题目限制**：一个想用 800MB 的程序，若笼子设 256MB，它会在 203MB 处被截断 ——
  `ru_maxrss` 只测到 203MB，**反而没超，漏网**。笼子装得太矮，测不到小偷拿了多少。
- 类比：**笼子是防弹门**（拦住最凶的），**峰值记录是监控录像**（看清他拿了多少）。

**设置（子进程里、exec 之前，和 `alarm(2)` 并排）：**

```cpp
struct rlimit lim;
lim.rlim_cur = 1024LL * 1024 * 1024;
lim.rlim_max = 1024LL * 1024 * 1024;
setrlimit(RLIMIT_AS, &lim);
```

- **软硬限制都要填**：`rlim_cur`（软）和 `rlim_max`（硬）。只填软的，用户程序自己一句
  `setrlimit` 就能把闸门抬到硬限制；两个都钉死才撬不动。

**测量（把 `waitpid` 换成 `wait4`，多一个参数接"账本"）：**

```cpp
struct rusage ru;
wait4(run_pid, &run_status, 0, &ru);   // 第 4 个参数：账本写到哪
// ru.ru_maxrss = 峰值 RSS，单位 KB（Linux）
```

- `&lim` 是**输入**参数（调用前我填好）；`&ru` 是**输出**参数（调用后内核填好），方向相反
- **单位坑**：`ru_maxrss` 是 **KB**，题目限制说 **MB**。`256 * 1024` 才能比。拿两个不同单位的
  数直接比，又是一个"不报错、安静地算错"的坑。

**实测数据：**

| 程序 | 峰值 RSS | 判定 |
| --- | --- | --- |
| `test.cpp`（a + b） | 3584 KB | AC |
| 一次 `new` 3GB 但一页不碰 | —— | AC（没占物理内存，判题器无感） |
| 真正写满 800MB | 822784 KB | **MLE** |
| 死循环 `while(true){}` | 1024 KB | TLE |
| 空指针写入 | 1024 KB | RE (signal 11) |

### 9. 内存超限的两种表现

- **撞到 `RLIMIT_AS`**：`new` 抛 `std::bad_alloc` → 程序没人 catch → `std::terminate()` →
  `abort()` → **SIGABRT(6)** → 判题器只会报 `Runtime Error (signal 6)`
  - **不能**靠"看到信号 6 就判 MLE"——用户自己 `abort()`、`assert` 失败、`vector::at()`
    越界没接住，全都是信号 6
  - **信号像火警铃**：它只说"出事了"，说不出"烧到多少度"。要判 MLE 必须靠**测量**
- **靠 `ru_maxrss` 测量**：拿到的是一个**数字**（用了多少 KB），才能和限制比大小

### 10. 拆函数（模块化）

**拆出两个函数，`main` 从 164 行降到 35 行**，读起来像一份目录：

```cpp
int main(...)
{
    if (!compile(argv[1])) return 1;      // 编译一次

    for (int i = 1;; i++)                  // 逐组跑
    {
        // 探路 → cout << "Test i"
        if (run_one_test(in_path, ans_path)) passed++;
        else return 1;
    }
    if (passed == 0) { ... }               // 空数据保护
    cout << "all " << passed << " test passed\n";
}
```

| 函数 | 签名 | 职责 |
| --- | --- | --- |
| `compile` | `bool compile(string src)` | 编译 + 抓取 g++ 报错 |
| `run_one_test` | `bool run_one_test(string in_path, string ans_path)` | 跑一组数据 + 判定 + 比对 |

#### 10.1 返回值都取 `bool`，不用 `int`

**问：`main` 拿到结果后需要知道什么？**

- `compile`：只要知道"成没成"
- `run_one_test`：一组测试有五种结局（AC/WA/TLE/RE/MLE），但 `main` 只需要知道
  **"过没过"** —— 具体是哪种，函数内部已经打印了（跟 `compile` 自己打印 `Compile Error` 一样）
- 所以 `true` = 通过，`false` = 不通过。**谁做的事谁负责报告**

**为什么不用 `int` 返回码？**

- 得先发明一张对照表（`0 = AC？1 = WA？2 = TLE？`），之后每读一行代码都要查表
- 更别扭的是那个 `0`：按退出码的直觉 `0` 表示成功，在这里却要表示 AC —— **同一套约定打架**
- 这与"`return 1` 在 `main` 里是进程失败、搬进函数后含义就变了"是同一个形状

#### 10.2 子进程只能 `_exit()`，父进程只能 `return`（这条坑踩了两次）

- 子进程 `return` 只是**从函数返回**，会回到 `main` 继续跑判题循环 →
  本该结束的子进程活着，与父进程**同时判题**、抢同一个 `output.txt`
- 反过来：父进程**绝不能** `_exit()` —— 那是在判题器自己身上动手，程序当场暴毙
- **判据不是"写的是不是 `return 1`"，而是"这一行跑在哪个进程里"** ——
  看它在不在 `if (pid == 0) { ... }` 的大括号内
- `run_one_test` 里的分布：子进程 **2 处** `_exit(1)`（`open failed` / `run exec failed`），
  父进程 **3 处** `return false`（MLE / 信号 / WA），外加 AC 的 `return true`
- 这些路径平时走不到（`execlp` 成功时进程映像直接被替换），是**潜伏的雷**

#### 10.3 大括号错位：一个"死人"的复活

- 搬代码时少了 `for` 的结束大括号，`if (passed == 0)` 和 `cout << "all " ...` 被吞进循环
- **现象**：`all 1 test passed` / `all 2 test passed` 每跑完一组就打印一次（本该最后只打一次）
- **后果**：循环里的 `if (passed == 0)` 永不成立 —— 能执行到那儿的都是刚 AC 的，`passed >= 1`
  → **空数据保护失效**，第 7 节那个"假通过"第 3 条**复活**
- **编译器不报错**，只能从输出看出来 → 又一次"安静地说谎"
- 教训：大括号对不上时，代码会被归到错误的层级，**编译器不会替你发现**

#### 10.4 回归验证：六条判定全部实测

| 用例 | 判定 | 关键输出 | 退出码 |
| --- | --- | --- | --- |
| `test.cpp` | AC | `all 3 test passed`（只出现一次） | 0 |
| `ce.cpp`（故意少分号） | CE | `Compile Error (exit code 1)`，g++ 报错原样抓回 | 1 |
| 把 `2.ans` 改成 999 | WA | `WA`，且**立刻停住**不再跑 Test 3 | 1 |
| `tle.cpp` | TLE | `Time Limit Exceeded`，1024 KB | 1 |
| `re.cpp` | RE | `Runtime Error (signal 11)`，1024 KB | 1 |
| `bigmem.cpp` | MLE | `822912 KB` | 1 |
| 空目录 | —— | `no test data found` | 1 |

**回归用例已入库**（`judge_demo/` 下）：`ce.cpp` / `tle.cpp` / `re.cpp` / `bigmem.cpp`。
WA 需要一个"答案不对"的场景，用临时复制一份数据、改掉某个 `.ans` 的方式测，不入库。
`ce.cpp` 是**故意写错**的，它的"错误"就是它的用途 —— 别顺手修好它。

#### 10.5 `ru_maxrss` 是测量值，不是常数

- 同一个 `bigmem.cpp`，三次实测：`822784` / `822784` / `822912` KB
- 它受环境变量、动态库布局等影响，**每次跑都会浮动**
- 阈值 256MB 离 800MB 很远，判定不受影响；但**卡在限制边缘的程序可能一次判 MLE、一次判 AC**

#### 10.6 diff 里的缩进噪音

- 拆掉 `main` 外层 `else` 后，函数体整体左移 4 空格 → `git diff --stat` 显示 126 增 / 118 删
- `git diff -w --stat`（`-w` = ignore whitespace）→ **31 增 / 23 删**，这才是真正的逻辑改动
- 行数只反映**阅读量**，不反映危险性：漏掉 `compile()` 那次是纯删除、一行新代码都没加，却致命

### 11. 同一个陷阱的三种面貌：你跑的不是你以为的程序

一天里撞了三次，全是同一件事：

| 你以为在跑 | 实际在跑 | 怎么暴露的 |
| --- | --- | --- |
| 新编译出来的用户程序 | 上一轮**残留的 `test` 二进制** | `rm -f test` 后再跑，才报 `run exec failed` |
| 真实的判题结果 | 用残留 `test` 跑出的**假 AC** | 同上 |
| 刚改好的判题器 | **改之前编译的旧 `judge`** | `all 1/2 test passed` 出现的位置不对 |

**共性**：源码、二进制、你实际运行的那份，三者脱节了。

**对策**

- 改完源码，**第一件事是重新编译**
- 结果"不对劲"时，**先确认跑的是不是新程序**，再怀疑逻辑
- 当行为测试分不出新旧时（重构后的程序本来就该跑出一样的结果），查**身外之物**：
  - `ls -l --time-style=+%H:%M:%S judge judge.cpp` —— 时间戳谁更新
  - `nm judge | grep run_one_test` —— 二进制里到底有没有这个符号
  - `grep -n "run_one_test" judge.cpp` —— 源码里有没有
- **临时文件用完就清**：残留的 `test` 二进制、`output.txt` —— 它们都会替 bug 打掩护

**仓库也一样**：本地仓库、服务器仓库、GitHub 三者同样会脱节。`push` 被拒就是这个信号 ——
先 `git pull --rebase` 再 push。`rebase` 会重写提交，hash 变化是正常的。

### 12. 隐含假设：判题器假设「我是这个目录里唯一的程序」

**背景**：判题器一直是命令行手动跑的（`./judge <源文件> <数据目录>`）。挂到 Web 层之后，
Flask 用 `subprocess.run` 调它 —— **每次 HTTP 提交都起一个判题进程**。

**现象**：同一份**完全正确**的代码，8 个并发提交，只有 1 个判对：

```
exit code: 1     ← 判错了
exit code: 1
exit code: 1
exit code: 1
exit code: 1
exit code: 1
exit code: 1
exit code: 0     ← 只有这一个是对的
```

**三处资源写死在当前工作目录、名字还固定：**

| 文件 | 谁写的 | 冲突后果 |
| --- | --- | --- |
| `submission.cpp` | Web 层写进去的用户源码 | 后一个请求覆盖前一个 → A 编译到的是 B 的代码 |
| `test` | 判题器 `g++ -o test` | B 的编译覆盖 A 的可执行文件 → A 的测试点跑的是 B 的程序 |
| `output.txt` | 判题器重定向的运行输出 | 两边共用一个文件 → A 读到 B 的输出 → **误判 WA** |

**判题器本身一行没错。** 它只是依赖了一个**从没被写下来的假设**：

> 「我是这个目录里唯一在跑的程序。」

这个假设在命令行下**永远成立**（一次只跑一个），所以它在 `judge_demo` 里稳稳跑了好几天、六判定全通。
**一挂到 Web 上立刻碎掉** —— 并发是 Web 的天性，不是你额外加的功能。

**修法**（`web/app.py`）：每次提交开一间独立的临时目录。

```python
work_dir = tempfile.mkdtemp()                    # 全系统唯一的空目录
src_path = os.path.join(work_dir, "submission.cpp")
...
result = subprocess.run(
    [JUDGE_BIN, src_path, TESTDATA_DIR],         # 全改绝对路径
    cwd=work_dir,                                # 在「这间房间」里跑
    ...
)
shutil.rmtree(work_dir, ignore_errors=True)      # 判完拆掉
```

**修完重跑同一实验：8 个并发 → 8 个 `exit code: 0`。**

#### 12.1 改 `cwd` 会让所有相对路径失效

原来写的是 `["./judge", "submission.cpp", "testdata"]`，能跑是因为 `cwd` **恰好**是 `judge_demo`。
`cwd` 一换成临时目录，同样的相对路径就变成「在 `/tmp/tmpXXXX` 里找 `./judge`」—— 找不到。

所以 `JUDGE_BIN` / `TESTDATA_DIR` 必须改成绝对路径。**改 `cwd` 的瞬间，代码里每一个相对路径的含义都跟着变了。**

#### 12.2 教训

- **「能跑」不等于「对」。** 一个程序稳定跑几天，可能只是因为它的隐含假设一直没被挑战。
- **从单机程序变成服务的一部分时，先问一句：它偷偷依赖了什么？**
  （工作目录、固定文件名、全局变量、端口、单实例……）
- 这是第 11 节那个主题的**第四次**变体：**你跑的不是你以为的程序** —— 这次是 Web 层在跑别人的代码。

### 13. 异步判题：把「判题」从「请求」里搬出去

**背景**：第 12 节修完并发之后，Web 层是这么写的 ——

```python
result = subprocess.run([JUDGE_BIN, src_path, TESTDATA_DIR], cwd=work_dir, ...)
return "<pre>" + result.stdout + "</pre>"
```

`subprocess.run` 是**同步等待**：HTTP 请求要一直挂到判题跑完。判题要 2 秒，请求就得占着 2 秒。

**实测**（同一个 TLE 程序 `int main(){while(true){}}`）：

| 场景 | 用时 |
| --- | --- |
| 单个提交 | 2.10s |
| 8 个并发提交 | 每个 ~2.5s |

第二行值得注意：**请求没有排队，是并行的**。Flask 自带的开发服务器默认多线程，8 个请求
开了 8 条线程、8 个判题进程同时在跑 —— 而服务器只有 2 核。

所以问题不是「服务撑不住」，是**用户必须干等** —— 而且等待期间，服务器上占着一条线程 +
一个判题进程，等完才释放。

**改法**：把判题从请求里搬出去，请求只负责「收下」。

```
浏览器 ──POST──> Flask ──> 丢进队列 ──> 立刻返回「已接收，编号 xxx」
                              │
                              └──> 后台工人 ──> 判题器 ──> 结果写进任务表

浏览器 ──GET /result/编号──> 查任务表
```

三样新东西：

| 东西 | 代码 | 作用 |
| --- | --- | --- |
| 传送带 | `job_queue = queue.Queue()` | 先进先出。`get()` 在队列空时**睡着等**，不烧 CPU，有东西进来立刻醒 |
| 工人 | `worker()` + `threading.Thread(...)` × 2 | 死循环取任务。开 2 个，对应 2 核 |
| 任务表 | `jobs = {}` + `jobs_lock` | 编号 → 状态。**任务有了自己的身份**，不再跟请求绑死 |

`/submit` 变成：写临时目录 → 生成 `job_id` → 登记任务表 → `put` 进队列 → **立刻 return**。
判题那一步从 `/submit` 搬进了 `worker()`，`shutil.rmtree` 也跟着搬过去（判完才拆，不是提交完就拆）。

**实测**（同一个 TLE 程序）：

| | 用时 | 页面显示 |
| --- | --- | --- |
| 改之前 | 2.10s | 白屏干等 2 秒，然后跳出判题结果 |
| 改之后 | 0.0032s | 立刻「已接收，编号 873eb843」 |

**快 650 倍 —— 因为判题根本没发生在这个请求里。** 判题还是那 2 秒，只是搬到另一条线上去了。

#### 13.1 `except` 不写，工人会悄悄死掉

`worker()` 是个 `while True:` 线程。里面抛了没接住的异常，**这个工人就死了** ——
而且是静默的，没有任何报错。工人一死，队列里塞多少任务都没人取：
POST 照常秒回「已接收」，结果**永远停在「排队中」**。

```python
try:
    result = subprocess.run(...)
except Exception as e:
    text = "判题器出错了：" + repr(e)          # 炸了也要留下痕迹
finally:
    shutil.rmtree(work_dir, ignore_errors=True)   # 炸没炸都要把目录拆掉
```

这是队列架构的经典坑：**消费者死了，队列不会告诉你，它只会变长。**

#### 13.2 顺带撞上的新变体：本机通 ≠ 外网通

浏览器打不开 `http://106.55.253.184:5000`，但服务器上 `curl 127.0.0.1:5000` 返回 HTTP 200。

| 从哪测 | 结果 |
| --- | --- |
| 服务器自己 `curl 127.0.0.1:5000` | HTTP 200 |
| 外网（Windows 本机） | 8 秒超时 |
| 服务器 ufw | inactive（压根没开） |
| 服务器 iptables | 只有几条挡「扫 SSH 的陌生 IP」，没拦 5000 |

拦在**腾讯云安全组** —— 控制台里那张「外面能敲哪些端口」的表。它和 OS 层的 ufw / iptables
是**两套东西**：服务器内部那道门没关，是外面那道门没开。

开发期绕过办法：`ssh -N -L 5000:127.0.0.1:5000 vps`，把服务器端口接到本机的 5000，
浏览器访问 `http://127.0.0.1:5000/`。不经过安全组，也不把端口暴露到公网。

**这是第 11 / 12 节那个主题的第五次变体。** 前四次是「你以为在跑 A，其实跑的是 B」，
这次是「**你以为测通了，其实测的是别人走不到的那条路**」。

## 已知问题 / 待改进

- **判定优先级**：当前 MLE 检查排在信号判定**之前**，所以一个"又死循环又吃内存"的程序会被
  报成 MLE 而不是 TLE。严格说 TLE 应优先 —— 被闹钟半路砍掉的程序没跑完，它的内存峰值不完整，
  不能代表真实需求。现有测试用例均未触及此边界。
- **内存不能中途拦截**：现在是"等程序跑完（或被砍）再算账"。更严格的 OJ 会在运行中**轮询**
  `/proc/<pid>/status`，一超限立刻杀掉，避免 2 秒内真的吃掉大量内存。本项目未实现。
- **`ru_maxrss` 有测量浮动**：同一程序多次运行可差几十~几百 KB（实测 `822784` / `822912`）。
  卡在限制边缘的程序可能出现"一次 MLE、一次 AC"的抖动。严格 OJ 会给容差，或改用更稳定的测量方式。
- 并发判题时 `setrlimit` 的宽限额（1GB）仍可能被多个进程同时占满，真正的隔离需要 cgroup。
- **`jobs` 字典只增不减**：每条提交都往内存里塞一条记录，判完也不清理，跑久了内存一直涨。
  而且它是**进程内存**，Flask 一重启所有提交记录就没了 —— 任务表该落库（MySQL），这一步一并解决。
