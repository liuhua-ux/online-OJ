# 1 引言

## 1.1 目的

本文档定义**在线判题系统（Online Judge，以下简称 OJ）**的功能需求与非功能需求，作为后续概要设计、详细设计、编码实现与测试验收的统一依据。本文档在项目组与相关成员（指导教师、开发者、测试人员）之间建立一致的需求描述，并作为需求变更与验收对照的基线。

## 1.2 背景

- **软件系统名称**：在线判题系统；英文缩写 **OJ**；项目编号 OJ-2026。
- **任务提出者**：网络空间安全学院《软件工程实验》课程（指导教师：甘文生）。
- **开发者**：刘逸涵（网络空间安全学院 2024 级 1 班，学号 2024103652）。
- **应用范围**：面向编程教学与自主训练场景，提供题目浏览、代码在线提交、自动编译运行与判定、判题结果反馈、排行榜等功能。系统采用 B/S 架构，通过浏览器访问。
- **用户**：学生（普通用户）与管理员。
- **产生需求的原因**：编程训练中，人工验证提交代码的正确性耗时且主观；本地评测无法约束运行时间与内存，也无法统一管理题目与提交记录。本系统将"编译—运行—比对—判定"流程自动化，并以统一题目库与提交记录支撑教学与训练。

| 模块名 | 模块缩写 | 模块名 | 模块缩写 |
|---|---|---|---|
| 用户与权限 | USR | 代码提交 | SUB |
| 题库管理 | PRB | 判题引擎 | JDG |
| 测试用例管理 | TST | 提交记录 | REC |
| 排行榜 | RNK | 系统管理 | SYS |

需求标识在整个项目中唯一，且**不随需求变更而改变**——需求作废时保留编号并标注"已作废"，新需求另取新号。不使用 Word 自带的自动序列号作为需求标识。

**2）需求的跟踪粒度。** 跟踪到第二层（模块 → 主功能点），第三层（主功能点下的具体规则）只做描述、不单独编号。

**3）优先级定义。** 本文档的优先级分为三级：

| 级别 | 含义 |
|---|---|
| 高 | 缺此功能系统不能完成核心流程，必须在第一版实现 |
| 中 | 影响体验或完整性，应在第一版实现，可延后至第二版 |
| 低 | 锦上添花，可延后 |

**4）实现进度标注约定。** 本文档描述的是**目标系统**的完整需求，不等同于当前已完成的部分。为便于评审对照，在需求条目后统一标注实现进度：

| 标记 | 含义 |
|---|---|
| ★ 已实现 | 已编码并实测通过，可在服务器上演示 |
| ☆ 部分实现 | 骨架可用但功能不完整 |
| ○ 待实现 | 尚未编码 |

**5）功能描述方法。** 第 3 章对每个功能点按以下要素描述：业务定义/描述、适用的用户类型、业务规则/业务要素、主要页面或样式、输入、输出、业务操作流程（含异常流程）、约束条件/特殊考虑。

**6）界面描述规则。** 本阶段以文字描述页面构成与控件；用例图、界面原型图（draw.io / PlantUML）在概要设计阶段补充，并入本文档附件。

**8）分期目标。** 本项目分两期实现。两期的**功能范围完全一致**（即本文档第 3 章的全部需求），差别只在 Web 层的实现方式：

| 期次 | Web 层 | 判题层 | 目标 |
|---|---|---|---|

# 2 项目概述

## 2.1 系统功能

系统按"用户—题库—提交—判题—成绩"主线组织，功能结构如下：

```
在线判题系统
├── 用户与权限 (USR)
│   ├── 注册
│   ├── 登录 / 注销
│   └── 个人信息查看与修改
├── 题库管理 (PRB)
│   ├── 题目列表浏览
│   ├── 题目详情查看
│   └── 题目新增 / 编辑 / 删除        [管理员]
├── 测试用例管理 (TST)
│   └── 测试用例新增 / 编辑 / 删除    [管理员]
├── 代码提交与判题 (SUB / JDG)
│   ├── 在线提交代码
│   ├── 编译（CE 判定）
│   ├── 逐测试点运行与比对（AC / WA）
│   ├── 时间限制（TLE）
│   ├── 内存限制（MLE）
│   ├── 运行时错误判定（RE）
│   └── 异步排队与并发调度
├── 提交记录 (REC)
│   ├── 单次提交结果查看
│   └── 历史提交列表查询
├── 排行榜 (RNK)
│   └── 按通过题数 / 总分排序
└── 系统管理 (SYS)
    └── 用户管理                    [管理员]
```

功能分类与优先级概览：

| 功能分类 | 包含模块 | 优先级 |
|---|---|---|
| 判题核心 | SUB、JDG | 高 |
| 题库与用例 | PRB、TST | 高 |
| 用户与权限 | USR | 高 |
| 提交记录 | REC | 高 |
| 并发调度 | JDG | 高 |
| 排行榜 | RNK | 中 |
| 系统管理 | SYS | 中 |

## 2.2 业务描述

系统主业务流程如下：

```
学生                        系统                          管理员
 │                           │                              │
 │                           │  ←── 出题 + 配置测试用例 ──── │
 │                           │                              │
 ├─ 注册 / 登录 ───────────→ │ 校验身份、建立会话            │
 │                           │                              │
 ├─ 浏览题目列表 ──────────→ │ 查询题目库                    │
 ├─ 打开题目详情 ──────────→ │ 返回题面 + 输入输出说明       │
 │                           │                              │
 ├─ 编写 / 粘贴代码并提交 ─→ │ 落库（status = 排队中）       │
 │                           │                              │
 │                           ├─ 判题引擎取任务：            │
 │                           │  ① 编译 → 失败则 CE          │
 │                           │  ② 逐测试点运行               │
 │                           │  ③ 比对输出 → AC / WA        │
 │                           │  ④ 超时 / 超内存 / 信号 →     │
 │                           │     TLE / MLE / RE           │
 │                           │  ⑤ 写回结果                  │
 │                           │                              │
 │ ←─ 查看判定结果 ──────────┤ 返回状态码、耗时、峰值内存    │
 ├─ 查询历史提交 ──────────→ │ 返回该用户提交记录            │
 └─ 查看排行榜 ────────────→ │ 按通过题数 / 总分排序         │
```

业务要点：

1. **判题是异步的。** 提交后接口立即返回"已接收（排队中）"，判题在后台执行，前端轮询或刷新查看结果。这样并发提交时前端不阻塞，也避免 HTTP 请求超时。
2. **判题结果由程序消费，不是给人看屏幕。** 判题器对外只交付**退出码**（0 = 全部测试点通过，非 0 = 不通过），屏幕上的 `AC` / `WA` 文字仅供人工调试。Web 层只读退出码决定写入数据库的状态。
3. **题目与测试用例分离。** 题目是可读文本，测试用例是运行数据；一道题可含多个测试点，测试点的增删不改动代码逻辑。

## 2.3 数据流程描述

系统数据流如下：

```
管理员 ──题面/说明──→ [题目表 problems]
      └─用例数据───→ [测试用例表 testcases] ──落盘──→ 数据目录 N.in / N.ans
                                                          │
学生 ──源码──→ [提交表 submissions] ──取源码──→ 源码文件 ─┘
                                                          ↓
                                                    [判题引擎]
                                                    编译 / 运行 / 比对
                                                          ↓
学生 ←──结果── [提交表（状态、耗时、峰值内存）] ←──────────┘
                                                          │
                                            通过记录 ──→ [排行榜：Redis 缓存]
```

**数据存储说明：**

- **MySQL**：题目、测试用例元信息、提交记录、用户信息。属于持久化数据，不可丢失。
- **Redis**：排行榜缓存。属于可重建的派生数据，丢失后可由提交记录重新生成。
- **文件系统**：每题一个测试数据目录（`1.in` / `1.ans` / `2.in` / `2.ans` …）；每次判题产生中间产物（用户源码文件、编译出的可执行文件、运行输出文件），属临时数据，判题结束后清理。

## 2.4 用户的特点

| 用户类 | 特征 | 使用频度 | 相关需求 |
|---|---|---|---|
| 一般操作者（学生） | 具备基础 C++ 编程能力；熟悉浏览器与文本编辑，无需了解系统内部实现；提交频繁且可能并发集中 | 高（训练期每天多次） | USR、PRB、SUB、REC、RNK |

## 2.6 设计和实现上的限制

1. **语言限制**：第一版仅支持 C++（C++11/17）判题。多语言支持需要为每种语言配置独立的编译与运行命令，属需求变更（见第 7 章）。
2. **编译器依赖**：判题正确性依赖服务端安装 g++。若 g++ 缺失或不可执行，判题器应返回 SE 而非误判。
3. **系统调用依赖**：判题依赖 Linux 专有机制（`fork` / `exec` / `setrlimit` / `wait4` / 信号）。系统不能在 Windows 上直接运行判题器。
4. **隔离强度限制**：当前采用 `setrlimit` 做资源约束，属**同机同用户**的软隔离，达不到生产级沙箱强度（对比：cgroup + namespace + seccomp）。多进程并发时，宽限额仍可能被同时占满。
5. **判题器工作目录限制**：判题器当前的中间产物（可执行文件 `test`、运行输出 `output.txt`）写在**当前工作目录**。多人并发提交会互相覆盖，导致误判（已实测复现：一份正确代码被判为 WA）。**每次提交必须使用独立临时工作目录**——这是必须解决的实现约束，见 `OJ-JDG-07`。
6. **经费与资源限制**：单台 VPS，CPU 与内存有限，并发判题能力受限于机器核数。
7. **进度限制**：项目按课程实验进度推进，需在课程结束前完成"可演示"版本。

### 3.1.2 用户登录与注销 `OJ-USR-02` — ★ 已实现

## 3.3 测试用例管理（TST）

### 3.3.1 测试用例新增 / 编辑 / 删除 `OJ-TST-01` — ★ 已实现

- **业务定义/描述**：为每道题维护"标准输入 + 标准答案"的测试点集合，作为判题依据。
- **适用的用户类型**：管理员。
- **业务规则/业务要素**：
  - 一道题可含多个测试点，判题时**按顺序逐个运行**，遇到不通过立即停止（不再跑后面的测试点）。
  - 测试点以文件形式落盘，命名规则固定为 `<目录>/<序号>.in` 与 `<目录>/<序号>.ans`，**序号从 1 开始连续编号**（`1.in` 而非 `0.in`）。
  - 判题器通过"探测文件是否存在"来判断还有没有下一组数据，因此**序号不得跳号**：若删掉 `2.in` 而保留 `3.in`，判题器会在第 2 组停止，第 3 组永远不会被执行。
  - 题目必须至少有一个测试点。
- **主要页面**：题目编辑页中的测试用例区（新增 / 删除按钮 + 每个用例的输入框与答案框）。
- **输入**：标准输入文本、标准答案文本。
- **输出**：用例保存成功；题目详情页显示"共 N 个测试点"。
- **业务操作流程**：
  - 正常流程：添加用例 → 填写输入与答案 → 保存 → 重排序号并落盘。
  - 异常流程：删除中间某个用例 → **必须重编号**，保证 1..N 连续；保存失败 → 提示并保留原数据。
- **约束条件/特殊考虑**：
  - 序号连续性是最容易出错的地方，属"编译器不报错、程序安静地跑错"的类型，必须由服务端统一重编号，不依赖管理员手工命名。
  - 用例数据量较大时，不宜存入数据库文本字段，应直接落盘并在数据库中仅存元信息（序号、文件路径、大小）。
- **实现状态**：★ 已实现并实测（`7944581`）。
  - **落盘方案**：测试点内容在 `judge_demo/testdata/<题号>/<序号>.in|.ans`，数据库 `testcases` 表只存序号 / 相对路径 / 字节数，`UNIQUE (problem_id, ordinal)` 由数据库保证序号不重复；判题器按题号读取各自目录（`76dff6a`）。
  - **界面**：题目编辑页下半部分即测试用例区，每个测试点两个文本框（输入 / 答案），末尾常留一个空位，另有「＋ 再加一个空位」链接（纯链接，不需要 JavaScript）。表单**提交的是整份状态**而不是「增/删/改」指令 —— 所以同样的内容交两次结果一样（幂等），加组删组也不必维护组号。
  - **重编号与残留清理**：服务端按顺序对非空的组重新编号 1..N，**落盘前先把 `testdata/<题号>/` 整个清空**。实测：三组中删掉中间那组后，目录里只剩 `1.in/1.ans/2.in/2.ans`（`3.*` **确实消失**），`2.in` 的内容变成原第 3 组的 `-5 5`，重新提交后判题器报告 `all 2 test passed`。**若只覆盖前 N 个文件而不清理残留，判题器会把陈年的 `3.in` 当成「还有下一组」接着判**，这时它会报 `all 3 test passed` —— 测试点被重复执行，且数据是过期的。
  - **换行符**：浏览器提交的多行文本换行是 `\r\n`（HTTP 表单规范），落盘前统一归一化为 `\n`。实测反证：把 `testdata/1/1.ans` 的行尾由 `\n` 改成 `\r\n`，**同一份正确代码**从「3 组全 AC」变成第 1 组 `WA` 并立即停止（判题器 `judge.cpp` 是逐行 `getline` 后补 `\n` 再整串比较，多一个不可见的 `\r` 就不相等）。
  - **未做**：落盘不是原子操作，见 `FIX-20`。
  - **二期（2026-10-23）**：表单用重复的 `tc_in` / `tc_ans` 传递整份状态，服务端按出现顺序配对（C++ 侧为此新增 `parse_form_multi()`，因为 `map` 会丢掉同名参数）。实测三组删中间一组：盘上只剩 `1.in/1.ans/2.in/2.ans`，`2.in` 的内容变成原第 3 组的 `3 3`，**残留的 `3.in` 已消失**；数据库元信息在同一事务里 `DELETE` + `INSERT` 重编号。

### 3.4.2 编译与编译错误判定 `OJ-JDG-01` — ★ 已实现

- **业务定义/描述**：对提交的源码调用 g++ 编译；编译失败则直接判定为 CE，不进入运行阶段。
- **适用的用户类型**：系统自动执行，无须用户操作。
- **业务规则/业务要素**：
  - 编译只做一次，编译产物供所有测试点复用（避免每个测试点重复编译）。
  - 编译失败时**必须把 g++ 的原始报错信息回传给用户**，否则用户无法定位问题。
  - 编译失败返回 CE，不应报成 SE 或其他状态。
- **输入**：用户源码文件。
- **输出**：编译成功 → 可执行文件；编译失败 → CE 状态 + g++ 报错原文。
- **业务操作流程**：派生编译子进程 → 捕获其标准错误流 → 等待结束 → 依据退出码判定成败。
- **约束条件/特殊考虑**：编译器报错可能超过管道缓冲区容量（约 64 KB），若先等进程结束再读，会双向死锁；必须**先读取报错流至结束，再等待进程**。读取时要处理"短读"（一次读不完），需循环读取。
- **实测结果**：故意写错（少一个分号）的源码 → 输出 `Compile Error (exit code 1)`，g++ 报错原文被完整抓回，进程退出码 1。

### 3.4.3 逐测试点运行与输出比对 `OJ-JDG-02` — ★ 已实现

- **业务定义/描述**：对每个测试点，把标准输入喂给编译产物、收集其输出，与标准答案比对。
- **适用的用户类型**：系统自动执行。
- **业务规则/业务要素**：
  - **每个测试点使用独立子进程**运行，互不干扰（也保证每个测试点的计时与内存统计相互独立）。
  - 输入重定向至标准输入，输出重定向至文件。
  - 比对采用**逐行比较**，且**不得丢弃行边界**——否则输出 `3\n0` 与答案 `30` 会被误判为相等（详见"约束"）。
  - 遇到第一个不通过的测试点即停止，不再运行后续测试点。
  - 全部测试点通过才算通过。
- **输入**：`N.in` 与 `N.ans`，以及编译产物。
- **输出**：每个测试点的判定结果（AC / WA / TLE / MLE / RE）；完整通过时输出 `all N test passed` 与退出码 0。
- **业务操作流程**：对第 N 个测试点：探测 `N.ans` 是否存在 → 存在则提示"Test N" → 派生子进程运行 → 等待并采集状态与资源账本 → 判定 → 通过则继续 N+1，不通过则立即停止。
- **约束条件/特殊考虑**：
  - **"误判 AC" 远比 "误判 WA" 严重**——把错误答案当成正确答案，不会有任何人发现。因此比对宁可严格。
  - 输入输出用**文件**而非管道：管道有 64 KB 容量上限，大输出会造成死锁；文件方式天然对接比对逻辑，且便于调试。
  - 探测下一组数据是否存在这一步，**必须在父进程、派生之前完成**：需要它的是外层循环，而循环在父进程里；若交由子进程在打开失败后返回错误，会与用户程序自身的退出码混淆。
  - 提示文字（`Test N`）必须放在探测**之后**，否则会打印出一组并未真正运行的"空头支票"。

### 3.4.4 运行时间限制 `OJ-JDG-03` — ★ 已实现

- **业务定义/描述**：限制单个测试点的运行时间，超时终止进程并判定为 TLE。
- **适用的用户类型**：系统自动执行。
- **业务规则/业务要素**：每个测试点有独立的超时（当前为 2 秒）；超时后**必须真正终止**用户进程，不能只标记状态而让进程继续占用 CPU；`SIGALRM` 信号被视为超时。
- **输入**：超时时长。
- **输出**：TLE 状态；实测输出为 `Time Limit Exceeded`。
- **业务操作流程**：在子进程派生后、执行用户程序前设置闹钟 → 用户程序运行 → 到点收到信号被终止 → 父进程据信号号判定 TLE。
- **约束条件/特殊考虑**：
  - 闹钟的**设置位置只有一处是正确的**：必须在子进程内、执行用户程序之前。经验证：`fork` **不继承**闹钟（父进程定时被杀时子进程仍在运行），而 `exec` **保留**闹钟。
  - 每个测试点独立计时是自然实现的：每轮派生的都是全新子进程，闹钟自然重新计时。
  - **已解决（2026-10-26，`FIX-02`）**：判定顺序改为 **TLE → MLE → RE** —— 先看是否被闹钟中断，再看内存峰值，最后看其它信号。理由：被闹钟中断的程序没跑完，其内存峰值不完整，不能代表真实需求。实测：既死循环又吃内存的程序由 MLE 改判 TLE；纯超时 / 纯超内存 / 纯 RE / 正常 AC 四类判定均未受影响。
  - ⚠️ **宿主机直接运行时的耗时干扰（2026-10-26 实测）**：在宿主机上直接运行判题器（`main` 分支的开发 / 对照环境）时，本机 `core_pattern` 为管道模式（`|/usr/share/apport/apport`），内核在进程崩溃后会同步调用 apport 收集现场信息，`wait4` 要等其收工才返回 —— **RE 量出的耗时约为 1150 ms**，而程序本身只有数毫秒。判定结论不受影响（杀它的是 SIGSEGV 不是 SIGALRM），只是耗时数字偏高。
    **两种部署的差异**：**容器部署（`feat/public-deploy`）不受影响** —— 容器内没有 apport，同一用例实测 **201 ms**。修法（如要消除宿主机上的偏差）：把 `core_pattern` 改回普通文件模式（管道模式下内核不检查 `RLIMIT_CORE`），或关闭 apport。**当前未改，如实标注。**
- **实测结果**：死循环程序 → `Time Limit Exceeded`，峰值内存 1024 KB，退出码 1。

### 3.4.5 运行内存限制 `OJ-JDG-04` — ★ 已实现

- **业务定义/描述**：限制单个测试点的内存使用，超限判定为 MLE。
- **适用的用户类型**：系统自动执行。
- **业务规则/业务要素**：
  - **两套独立机制、各管各的**：
    | 机制 | 限制对象 | 数值 | 用途 |
    |---|---|---|---|
    | 地址空间上限（`RLIMIT_AS`） | 地址空间 | 宽松（演示用 1 GB） | **保命**：挡住 `new char[1TB]` 这类内存炸弹 |
    | 峰值物理内存（`ru_maxrss`）与题目限制比较 | 物理内存峰值（RSS） | 256 MB | **判分**：准确说明"你超了多少" |
  - **保命上限不能等同于题目限制**：若把保命上限设成题目限制（256 MB），一个想用 800 MB 的程序会在 203 MB 处被截断，`ru_maxrss` 只测到 203 MB，**反而没超限，成为漏网之鱼**。笼子装得太矮，测不出小偷拿了多少。
  - **软硬上限都要设置**：只设软上限时，用户程序自己调用一次 `setrlimit` 就能把闸门抬高；两个都钉死才撬不动。
- **输入**：题目内存限制（MB）。
- **输出**：MLE 状态；实测输出含峰值内存数值（如 `822912 KB`）。
- **业务操作流程**：子进程执行用户程序前设置地址空间上限 → 父进程等待时采集资源账本 → 取峰值 RSS 与题目限制比较 → 超限则 MLE。
- **约束条件/特殊考虑**：
  - **单位必须统一**：峰值 RSS 的单位是 KB，题目限制的单位是 MB，比较前须换算（`256 * 1024`）。直接比较两个不同单位的数会"不报错、安静地算错"。
  - **不能靠信号号判 MLE**：撞到地址空间上限时 `new` 抛异常 → 程序未捕获 → `abort()` → 信号 6。但用户自己调用 `abort()`、断言失败、容器越界未捕获，同样都是信号 6。**信号像火警铃，只说"出事了"，说不出"烧到多少度"**——判定 MLE 必须靠**测量**而非猜测。
  - **测量值有浮动**：同一程序多次运行，峰值 RSS 可相差数十至数百 KB（实测 `822784` / `822784` / `822912`）。阈值离边界很远时判定不受影响，但**卡在限制边缘的程序可能出现"一次 MLE、一次 AC"的抖动**。严格系统应给容差或改用更稳定的测量方式。
  - **无法中途拦截**：当前是"等程序跑完（或被终止）再算账"。更严格的系统会在运行中轮询 `/proc/<pid>/status`，一超限立即终止，避免 2 秒内真的吃掉大量内存。本项目暂未实现。
- **实测结果**：真正写满 800 MB 的程序 → 峰值 `822912 KB` → MLE，退出码 1；仅申请 3 GB 但一页不碰的程序 → 未占物理内存 → AC（判题器无感，符合预期）。

### 3.4.6 运行时错误判定 `OJ-JDG-05` — ★ 已实现

- **业务定义/描述**：用户程序被信号异常终止时判定为 RE。
- **适用的用户类型**：系统自动执行。
- **业务规则/业务要素**：区分"正常退出"与"被信号终止"两种结束方式：正常退出取退出码；被信号终止取信号号。`SIGSEGV`(11) 等异常信号判 RE；`SIGALRM`(14) 判 TLE。
- **输入**：子进程等待得到的状态。
- **输出**：RE 状态 + 信号号，实测输出为 `Runtime Error (signal 11)`。
- **业务操作流程**：等待子进程结束 → 判断结束方式 → 若是信号终止则取信号号 → 按信号号映射状态。
- **约束条件/特殊考虑**：**结束方式与退出码不可混用**——当进程是被信号终止时，取出的"退出码"没有任何意义，不能拿它做判定。
- **实测结果**：空指针写入的程序 → `Runtime Error (signal 11)`，峰值内存 1024 KB，退出码 1。

### 3.4.7 多测试点与工作目录隔离 `OJ-JDG-06` / `OJ-JDG-07`

**`OJ-JDG-06` 多测试点遍历 — ★ 已实现**

- **约束条件/特殊考虑**：

### 3.4.8 异步排队与并发调度 `OJ-JDG-08` — ★ 已实现

- **业务定义/描述**：提交后进入判题队列，由判题工作线程取出执行；多份提交并发处理。
- **适用的用户类型**：系统自动执行。
- **业务规则/业务要素**：
  - 提交接口**不阻塞等待判题结果**，只负责落库并返回"已接收"。
  - 队列**有界**：超出容量时拒绝新提交并明确提示，而不是无限堆积耗尽内存。

  - 同一份提交只被处理一次，不重复判题。
- **输入**：待判题的提交记录。
- **输出**：更新后的提交状态与判题结果。
- **业务操作流程**：提交入库 → 入队 → 工作线程取出 → 取源码与测试数据 → 调用判题器 → 读取退出码 → 写回结果 → 释放任务。
- **约束条件/特殊考虑**：
  - 多进程并发时，`setrlimit` 的宽限额（1 GB）仍可能被多个进程同时占满；**真正的隔离需要 cgroup**，本项目不实现。
  - 队列状态需要可观测：应记录队列长度与平均等待时间（见 `OJ-SYS-03`）。
- **实现状态（2026-10-04 实测）**：已实现主体。Web 层用 `queue.Queue` + 2 个后台守护线程（服务器 2 核）；`/submit` **先落库再入队**后立即返回提交号，不阻塞；结果页用 `<meta http-equiv='refresh'>` 轮询，判完即停。实测提交接口耗时由 2.10 s 降至 0.0032 s（差约三个数量级）。
  **一期未实现**：队列无界（`queue.Queue()` 未设 `maxsize`），工作线程数写死为 2，见 `FIX-12`。
  **已补（2026-10-25，二期）**：每次从队列取任务时记录 `queue len=<取完后队列长度> wait_ms=<从进入等待到拿到任务的毫秒数>`（`LOG_DEBUG` 级别），满足本条"队列状态可观测"。
  已加固：工作线程用 `try/except/finally` 包裹，避免异常导致线程静默退出、队列从此堵死。
  **已解决（2026-10-26，二期，`FIX-12`）**：队列改为**有界** —— `JUDGE_QUEUE_MAX = 64`，「判断容量 + 入队」在同一把锁内完成，避免多个工作线程同时看到"还剩一个位"；队列满时返回 **503**（带 `Retry-After: 5` 与整页提示），并**回滚刚落库的记录、删除临时目录**，不留下永远"排队中"的孤儿。判题线程数改为环境变量 `OJ_JUDGE_THREADS` 可配（有效范围 1–32，默认 2 —— 每个判题进程要派生 g++ 与测试点子进程，开多了会压住机器；非法值回落默认并记 WARN）。实测：把上限临时设为 1 后并发 4 份死循环提交，得到 302/302/302/503；被拒记录入库数 0、`/tmp` 无残留目录。

### 3.5.1 单次提交结果查看 `OJ-REC-01` — ★ 已实现

## 3.6 排行榜（RNK）

### 3.6.1 排行榜展示 `OJ-RNK-01` — ★ 已实现

- **业务定义/描述**：按通过题数与总分对所有用户排序展示。
- **适用的用户类型**：登录用户。
- **业务规则/业务要素**：

  - 排序依据：通过题数降序；题数相同则按总分 / 罚时（可选）排序。
  - 使用 Redis 缓存排行榜，避免每次访问都全表扫描提交记录。
- **主要页面**：排行榜页。
- **输入**：无（可选分页）。
- **输出**：排名、用户名、通过题数、总分。
- **业务操作流程**：正常流程：判题通过 → 更新该用户成绩 → 刷新缓存 → 页面读取缓存渲染。异常流程：缓存不可用 → 降级为直接查询数据库，**不得因缓存故障导致页面不可用**。
- **约束条件/特殊考虑**：排行榜是**派生数据**，Redis 中的数据可由提交记录完全重建，因此不需要持久化保障，缓存失效时可全量重算。
- **实现状态（2026-10-08 实测）**：★ 已实现（`bbc4375`）。`/rank` 展示「名次 / 用户 / 通过题数」，`db.rank()` 用 `COUNT(DISTINCT problem_id)` 落实「**同一题多次通过只算一次**」（防刷分），只统计 `verdict = 'AC'` 的提交。
  - ✅ **Redis 缓存**：键 `oj:rank`，TTL 60 秒；判题**通过**后主动失效（其他结论不会改变榜单，不必惊动缓存）。实测：第一次访问标注「直接查数据库」，第二次「Redis 缓存」。
  - ✅ **缓存故障降级**（本条点名要求「不得因缓存故障导致页面不可用」）：每一次 Redis 调用都**单独**包在 `try/except` 里 —— 读失败就当没有缓存去查库，写失败也无所谓。**实测：`systemctl stop redis-server` 之后，`/rank` 仍返回 200，数据正常显示，页面标注「直接查数据库」；Redis 恢复后自动回到「Redis 缓存」。**
  - 老提交（`FIX-06` 之前）没有 `verdict` 字段，**不计入榜单** —— 「没记过」不能当「通过了」用。

### 3.7.3 系统日志 `OJ-SYS-03` — ★ 已实现

- **业务定义/描述**：记录系统运行关键事件，供排查与审计。
- **业务规则/业务要素**：记录事件类型、时间、涉及用户与提交号、结果；输出包括判题耗时、峰值内存、异常堆栈摘要。
- **实现状态（2026-10-25，二期）**：已完成。新增独立模块 `oj_server/log.h` / `log.cpp`，接口 `log_init()` / `log_level_from_env()` / `log_write()` / `log_sanitize()`：
  - **级别**：`DEBUG` / `INFO` / `WARN` / `ERROR`，启动时读环境变量 `LOG_LEVEL` 设定阈值，低于阈值直接丢弃；

# 4 非功能需求

## 4.1 系统性能要求

**a. 时间特性**

- **单次判题响应时间**（不含排队）：**≤ 3 秒**。
  - 取值依据：单次判题耗时 ≈ 编译（约 0.5 秒）+ 最慢单测试点运行（限时 2 秒）+ 输出比对（约 0.1 秒）≈ 2.6 秒，取 **3 秒**并留有余量。
  - **说明一**：此指标针对"用户代码接近最优解、且耗时瓶颈集中在最慢的那一个测试点"的典型情况，以课程设计规模（单题测试点少量、程序规模小）估算。多个测试点均接近时限的极端情况不在此指标约束内。
  - **说明二**：编译只做一次，全部测试点复用同一编译产物，因此编译耗时只计一次，不随测试点数量增长。
- **并发提交**：支持 **50 个**提交同时进入排队而不阻塞提交接口。
  - 取值依据：由接入层与判题线程池（8～16 线程）加有界队列支撑；高于验证场景（同时 10 份提交），留有约 5 倍余量。
- **排行榜查询响应时间**：≤ 1 秒（由 Redis 缓存保障）。
- **页面加载时间**（题目列表 / 题目详情）：普通网络环境下 ≤ 2 秒。
- **时间测量单位**：秒（s），保留 3 位小数；内存单位为 KB / MB，展示时统一换算为 MB 并保留 2 位小数。

**b. 精度要求**

- 判题结果的判定**必须确定**：同一份代码与同一组数据，重复判题的结果应一致（例外：卡在时间 / 内存限制边缘的程序可能出现抖动，见 `OJ-JDG-04`）。
- 峰值内存为测量值，存在数十至数百 KB 的浮动，判定阈值须与之匹配。
- 输出比对为**精确文本比对**（逐行），不做浮点容差。若将来引入浮点答案，需在题目层面单独约定精度，属需求变更。

**c. 系统有效性**

- 服务端 7×24 小时可用（腾讯云 VPS 持续运行）；无计划内停机窗口。
- 判题高峰（课程训练集中提交时）不得导致提交接口不可用：提交接口与判题执行**解耦**，接口只做落库与入队。

**d. 容错性**

- **单个用户程序崩溃或恶意行为不得影响服务端**：内存炸弹被地址空间上限挡住，死循环被闹钟终止，段错误被限制在子进程内。
- 用户程序崩溃不得导致判题器进程退出异常或卡死。
- 缓存（Redis）故障时排行榜降级为直查数据库。
- 数据库连接失败时，接口返回明确的错误提示，不返回未处理的异常堆栈。

**e. 可扩充性**

- 判题器与 Web 层**解耦**：判题器是独立可执行程序，通过命令行参数与退出码交互，可单独测试、可替换实现。
- 判题器支持多测试点且**不需要预知测试点数量**，出题人增删数据不需修改代码。
- 新增编程语言支持应只需扩展"编译命令 + 运行命令"的配置，不改动判题主流程（当前架构尚未做到，列入第 7 章变更点）。
- 新增题目、新增用户均不需改动代码。

## 4.2 系统安全及保密要求

**1）访问控制**

- 功能按角色划分：学生可访问题库、提交、记录、排行榜；管理员额外可访问题目管理、用例管理、用户管理。
- **纵向越权防护**：管理员接口必须校验角色，不能仅靠前端隐藏按钮。
- **横向越权防护**：提交记录、个人信息必须校验"记录所属用户 == 当前用户"，不能只靠 URL 中的提交号。
- 未登录用户访问需授权页面时重定向至登录页。

**2）不可信代码隔离（本系统的核心安全需求）**

- 用户提交的代码是**不可信输入**，必须在受约束的子进程中运行：
  - 地址空间上限（`RLIMIT_AS`，演示用 1 GB）——防内存炸弹，用于**保命**；
  - 运行时间上限（闹钟，2 秒）——防死循环，超时**真正终止进程**；
  - 输入输出重定向至文件——避免管道容量导致死锁；
  - 每组测试点独立子进程——一次崩溃不影响后续判定与其它提交。
- **软硬资源上限均须设置**：仅设软上限时，用户程序可自行调用 `setrlimit` 抬高闸门。
- **隔离强度的诚实说明**：当前为**同机同用户**的软隔离，未使用 cgroup / namespace / seccomp，**达不到生产级沙箱强度**。多进程并发时宽限额可能被同时占满；用户程序理论上仍可访问文件系统。本项目作为课程设计不追求此强度，但必须在文档中如实标注（列入第 7 章）。
- **工作目录隔离**：每次判题使用独立临时工作目录，防止并发提交互相覆盖中间产物（`OJ-JDG-07`，当前未实现，为已知最严重缺陷）。

**3）口令与敏感数据**

- 口令加盐哈希存储，禁止明文与可逆加密。
- 登录失败提示**不区分**"用户名不存在"与"口令错误"，避免用户名枚举。
- 数据库连接信息、密钥等通过配置文件或环境变量注入，**不得硬编码进源码并提交到公开仓库**。

**4）审核记录**

- 记录登录事件、管理员的题目 / 用例增删改操作、判题系统错误，保留可追溯记录。
- 违反访问控制的行为（越权访问、未登录访问管理接口）应记录并监控。

**5）代码与题面注入防护**

- 题面、源码、运行输出在页面展示时须做 HTML 转义，防止 XSS。
- **源码绝不执行**于 Web 层进程内，只作为数据落盘后交由独立判题进程处理。

## 4.3 系统备份与恢复要求

| 信息类型 | 保存期 | 到期处理 |
|---|---|---|
| 题目与测试用例 | 长期（项目存续期） | 项目结束后归档 |
| 用户信息 | 长期 | 项目结束后删除 |
| 提交记录 | 项目存续期 | 项目结束后导出归档或删除 |
| 判题中间产物（源码副本、可执行文件、输出文件） | **判题结束后立即清理** | 删除 |
| 系统日志 | 建议 30 天 | 轮转或删除 |

- **备份方式**：MySQL 数据库定期逻辑备份；题目与测试用例数据目录随数据库一同备份；备份文件存放于服务器外部介质（本地磁盘另一分区或对象存储）。
- **恢复策略**：数据库可从最近一次备份恢复；Redis 排行榜数据**无需恢复**——它可由提交记录全量重算。
- **环境异常恢复**：VPS 故障时，代码由 GitHub 仓库恢复，数据由最近备份恢复。

## 4.4 系统日志

- **日志内容与记录策略**：记录时间、事件类型、用户、提交号、结果、判题耗时、峰值内存；判题相关日志与 Web 访问日志分离，便于排查。
- **保存时长与策略**：建议保留 30 天，超出后轮转或清理，避免占满磁盘。
- **访问控制**：日志仅管理员与运维者可访问，不通过 Web 界面对外暴露。
- **当前状态**：判题器目前直接向终端打印调试信息，尚无统一日志文件与级别划分（见 `OJ-SYS-03`）。

# 5 外部接口说明

## 5.1 硬件接口

- **服务器**：腾讯云 VPS，标准 x86-64 架构，无特殊外设要求。
- **客户端**：无特殊要求，任意可运行现代浏览器的设备。
- **约束**：并发判题能力受限于服务器 CPU 核数与内存容量；判题队列长度与工作线程数须据此配置。

## 5.2 软件接口

| 接口对象 | 版本 / 名称 | 输入输出关系 | 技术约束 |
|---|---|---|---|
| g++ 编译器 | 13.3.0 | 系统 → 编译器：用户源码；编译器 → 系统：可执行文件 + 报错信息 | 必须存在于服务端且可执行；报错通过标准错误流回传，须先读净再等待进程，避免缓冲区死锁 |
| Linux 内核 | Ubuntu 24.04 | 系统 → 内核：`fork` / `exec` / `setrlimit` / `alarm` / `wait4` / 信号 | 判题依赖 Linux 专有机制，不能移植到 Windows |
| 文件系统 | — | 系统 → 文件：测试数据、源码、编译产物、输出；文件 → 系统：读回比对 | 每次判题须使用独立临时目录（`OJ-JDG-07`）；测试点序号须从 1 连续编号 |
| MySQL | 8.0 | 系统 ↔ 数据库：题目、用例元信息、用户、提交记录读写 | 连接信息不得硬编码进公开仓库 |
| Redis | 7.0 | 系统 ↔ 缓存：排行榜读写 | 属可重建数据；故障时须降级为直查数据库 |
| Web 框架 | 一期：Python 3.12 + Flask 3.1.3；二期：自研 C++ 服务端（socket + epoll + 线程池） | 浏览器 ↔ 后端：HTTP 请求 / 响应 | 每次新终端须激活虚拟环境（`source venv/bin/activate`）；用户代码**不得**在 Web 进程内执行；两期共用同一套 HTTP 接口约定，故替换对浏览器端透明 |
| 版本控制 | Git + GitHub | 本地仓库 ↔ 远程仓库 | 服务器访问 GitHub 须走 SSH over 443（HTTPS 受限） |

## 5.3 通信接口

- **协议**：HTTP/1.1（后续可扩展为 HTTPS）。
- **交互方式**：
  - 页面导航：浏览器发起 GET 请求。
  - 代码提交：浏览器通过表单 **POST** 提交源码。
  - 结果获取：判题异步执行，前端通过**轮询**或页面刷新获取结果（当前实现为同步等待判题返回，属临时方案，需改为异步）。
- **技术约束**：
  - 提交接口须在判题开始前返回，避免 HTTP 请求超时。
  - 响应内容中的换行须正确保留（当前做法：使用 `<pre>` 标签）。
  - 中文与判题输出的字符编码统一为 UTF-8。

## 5.4 转换的安全考虑

- 源码从 HTTP 请求体到文件系统、再到编译进程的转换过程中**只作为数据**，不经过任何解释或求值。
- 编译与运行在独立子进程中进行，与 Web 服务进程隔离。
- 所有写入页面的用户可控内容（题面、源码、运行输出）须做 HTML 转义。

# 6 其他需求

**1）数据库需求**

实体与关系：

```
用户 (1) ──< 提交记录 (N) >── (1) 题目
题目 (1) ──< 测试用例 (N)
```

| 实体 | 主要属性 |
|---|---|
| 用户 | 用户 ID、用户名、口令哈希、角色、创建时间、状态 |
| 题目 | 题目 ID、标题、题面、输入格式、输出格式、时间限制、内存限制、数据目录、发布状态 |
| 测试用例 | 用例 ID、所属题目、序号、输入文件路径、答案文件路径 |
| 提交记录 | 提交号、用户 ID、题目 ID、源码、状态、通过数 / 总数、耗时、峰值内存、提交时间 |

字段级设计在详细设计阶段细化。**约束**：测试用例的"序号"字段必须保证同一题目内从 1 连续编号。

**2）法律与合规需求**

- 用户提交的代码版权归用户本人，系统仅在判题所必需的范围内使用与临时存储。
- 不收集与服务无关的个人信息；本项目不采集邮箱、手机号。
- 判题中间产物在判题结束后立即清理，不做长期留存。

**3）可移植性需求**

- Web 层为 Python，判题器为 C++，二者共同依赖 Linux。**移植到 Windows 需要重写判题器的进程管理与资源限制部分**，属重大变更。
- 尽量使用标准接口，减少对特定云厂商服务的耦合（当前仅使用 VPS，未使用云厂商专有服务）。

**4）重用性目标**

- 判题器作为**独立可执行程序**，不依赖 Web 层，可被其它系统（命令行工具、批处理脚本）直接调用——当前已是此形态。
- 判题器中"编译 → 运行 → 判定"的分工（`compile()` / `run_one_test()`）按职责拆分，可单独替换其中一环。

**5）用户操作需求**

- 提交代码为**复制粘贴**操作，不要求用户安装任何本地工具。
- 判题结果为异步获取，用户提交后可以继续浏览其它题目。
- 初始化操作：管理员需先创建题目与测试用例，系统方可被正常使用；空题库时页面应显示空状态而非报错。

> **对照压测（2026-10-23，同一台 2 核 VPS、回环网络、同一套压测脚本；GET 类 400 请求 / 16 并发，登录 80 请求 / 8 并发，各 3 轮取中位）**：
>
> | 场景 | 一期 Flask | 二期 C++（4 工人） |
> |---|---|---|
> | `GET /`（轻请求） | 919 QPS，p50 16.8 ms | **2309 QPS，p50 6.0 ms** |
> | `GET /problems`（查库渲染） | 36 QPS，p50 437 ms | **约 2000 QPS，p50 约 7 ms** |
> | `POST /login`（scrypt，纯 CPU） | 9.4 /s，p50 689 ms | **15.9 /s，p50 492 ms** |
>
> 三条结论：① 轻请求约 **2.3 倍**；② 查库页面约 **50 倍**，根因不是语言而是**每请求新建 MySQL 连接**（一期每次约 57 ms，16 并发全卡在握手上；二期用 `thread_local` 每工人一条常驻连接）；③ 只有 CPU 密集场景吃线程数 —— scrypt 在 1 工人时 8.5/s、4 工人时 15.9/s，恰好 2 核封顶；快请求在 1~4 工人之间**无差别**（主线程 epoll + MySQL 往返才是瓶颈）。压测程序与服务同机，绝对吞吐偏低，横向对比有效。
