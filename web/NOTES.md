# Web 层笔记（设计与进展）

> 记录 Web 层的核心设计决策与实测结论，可直接用作实验报告素材。
> 判题器本身记在 `judge_demo/NOTES.md`，这里只管 Web 层。

## 当前能力

一期 Web 层用 Python 3.12 + Flask 实现，跑在 VPS 上。

| 页面 | 路径 | 说明 |
| --- | --- | --- |
| 首页 | `/` | 占位 |
| 题目列表 | `/problems` | 题号 / 标题；空库显示「暂无题目」 |
| 题目详情 | `/problem/<题号>` | 题面 / 输入输出格式 / 样例 / 时限内存 / 共 N 个测试点 + **提交框** |
| 提交 | `/submit/<题号>` | 未登录 302 到 `/login`；裸 `/submit` 302 到 `/problems` |
| 结果 | `/result/<编号>` | 没判完自动刷新；判完停住 |
| 提交记录 | `/submissions` | 学生只列本人；管理员看全部可按用户名筛 |
| 排行榜 | `/rank` | 按通过题数排序（同题多次通过只算一次）；Redis 缓存 60 秒，**缓存挂了自动降级查库** |
| 注册 / 登录 / 退出 | `/register` `/login` `/logout` | |
| 我是谁 | `/whoami` | 演示 session 用 |
| 个人信息 | `/profile` | 用户名 / 角色 / 注册时间 + 修改口令（**必须提供原口令**） |
| 用户管理 | `/admin/users` | 列表 / 重置口令 / 禁用解禁 / 授予收回管理员　【管理员】 |
| 题目管理 | `/admin/problems` | 全部题目（草稿 / 已软删除的也看得见）；新建 / 编辑 / 删除入口　【管理员】 |
| 新建题目 | `/admin/problem/new` | 建成草稿；页面上没有「发布」勾选框　【管理员】 |
| 编辑题目 | `/admin/problem/<题号>/edit` | 题面表单 + **测试点管理区**；勾「发布」要求至少一个测试点　【管理员】 |
| 删除题目 | `/admin/problem/<题号>/delete` | **仅 POST**；软删除（`is_deleted = 1`）　【管理员】 |

关键实测：**提交从 2.10s 降到 0.0032s**（异步化）；**一次页面刷新 1.34ms CPU，判一次题 0.40s（AC）/ 2.05s（TLE）**——差两个数量级。

## 整体结构

```
浏览器 ──HTTP──> Flask (app.py)
                   │
                   ├─ 提交: 写临时目录 → 先落库(排队中) → 丢队列 → 立刻返回编号
                   │                              │
                   │                              └─> job_queue ──> worker ×2（后台线程）
                   │                                                    ├─ 拼出该题目录 testdata/<题号>/
                   │                                                    ├─ subprocess 跑 judge
                   │                                                    └─ 结果写回库(完成)
                   │
                   ├─ /result/<编号>: 查库；没判完带 <meta refresh 2> 自刷
                   ├─ /problem/<题号>: 题面 + 提交框
                   ├─ /admin/problem/…: 增删改（一律先过 admin_guard()）
                   │    编辑页保存时：测试点先落盘 → 再改库（顺序不能反，见 §19）
                   └─ nav(): 全站导航，每个页面都调它（只写一次）
                   │
                   └──> MySQL 库 oj

MySQL
 ├── users        用户（用户名唯一 + 密码哈希）
 ├── problems     题目（含时限/内存/发布标志/软删除标志）
 ├── testcases    测试点**元信息**（序号/路径/大小）—— 内容不在库里
 └── submissions  提交记录（编号/谁交的/哪道题/状态/结果/时间）

磁盘
 ├── judge_demo/judge                     判题器
 └── judge_demo/testdata/<题号>/<序号>.in|.ans   测试点的实际内容
```

## 关键设计决策

### 1. 异步判题队列（queue.Queue + 2 个工人线程）

- `/submit` 只做三件事：写临时目录 → 登记任务 → 丢队列，**立刻返回编号**
- 判题由后台 `worker` 线程做，判完写回数据库
- **`worker()` 里必须有 `try/except/finally` 三件套**：没有 `except` 的话，工人线程会**静默死掉**，队列从此堵死——POST 照常秒回，但结果永远停在「排队中」
- 服务器 2 核，所以开 2 个工人

### 2. 结果页自动刷新 + 超时兜底

- 没判完 → 返回带 `<meta http-equiv='refresh' content='2'>` 的页面；判完就不带（**页面停住 = 判完了**）
- 60 秒还没出结果 → 显示「判题异常」，不再无限转圈
- **超时用 `created_at` 时间戳判，不数刷新次数**：次数属于「这次页面访问」，按 F5 就归零；时间戳属于「这条提交」

### 3. 数据库：先落库，再排队（顺序不能反）

- 反了的话：工人可能先判完去 UPDATE，而记录还不存在 → **UPDATE 影响 0 行 → 结果永远丢失，记录卡在「排队中」**
- 每次操作各开各的连接（`db.py` 的 `connect()`），用完就关——因为连接不是线程安全的。**没有共用可变对象，所以并发不需要锁**

### 4. `commit` 的位置

- **commit 要放在「别人需要看见它」的最早时刻**，不是随便找个 `close()` 之前
- 实测（故意不 commit）：同一条连接 `INSERT` 后 `SELECT COUNT(*)` 数到 1，**另开一条连接数到 0**——自相矛盾且不报错
- 忘了 commit 的症状：提交成功、编号返回了，但 `/submissions` 永远没这条

### 5. 密码与登录

- 库里存 `scrypt:...` 哈希，**不存密码本身**（已在数据库里确认找不到明文）
- 盐让相同密码算出不同结果，废掉彩虹表；scrypt 故意算得慢
- **用户不存在 与 密码不对，故意返回同一句话**——防用户名枚举

### 6. 保持登录用「签名 cookie」，不用服务端名单

- 登录成功 → `session["username"] = 用户名`；之后每个请求 Flask 验签名 + 读票面
- **票面是 base64，不是加密**：解开就能看到 `{"username": "..."}`。防的是**篡改**（改票面 → `BadSignature`），不是偷看
- ⚠️ **`/logout` 其实作废不了票**：这个方案服务端不记名单，**没有能力**注销已发出的票，只能「劝浏览器把票删了」。退出后那张旧票**照样能冒充**
  → 这正是「退出所有设备 / 设备管理」背后必须有服务端名单的原因

### 7. 软删除的代价：过滤责任转移给了你

- 删一道题不是 `DELETE`，是 `is_deleted = 1`——**行还在**
- 于是**每一个查询都得自己记得写** `WHERE is_deleted = 0`，漏一个，被删的题就从某个角落冒出来
- **对比**：`UNIQUE` / 外键是**数据库替你兜底**（程序里的检查绕过程序就没了，数据库里的谁来了都绕不过）；软删除是**把兜底责任还给你**
- 为什么必须软删除：避免已产生的提交记录失去题目标题变成「孤儿记录」

### 8. 外键与唯一约束（交给数据库，不写进程序）

- `testcases`：`UNIQUE (problem_id, ordinal)` —— 让「序号不重复」由数据库保证，不靠人记得
- `submissions.problem_id` 外键指向 `problems`
- 实测：插重复序号 → `ERROR 1062 Duplicate entry`；插不存在的题号 → `ERROR 1452 foreign key constraint fails`

### 9. `schema.sql` 管「将来的库」，迁移文件管「现在这个库」

- `schema.sql` 里是 `CREATE TABLE IF NOT EXISTS` —— 表已经在了，**那句什么都不做**（实测：拿一句乱写的定义去建已存在的表，数据库一声不吭，表一个字段都没变）
- 所以给已存在的库加列必须写 `ALTER TABLE`，单独放 `migrate_*.sql`
- **带外键的表必须排在它引用的表后面**，否则建表失败——所以 `submissions` 在 `schema.sql` 里排在最后

### 10. 测试点落盘，库里只存元信息

- 文件在 `judge_demo/testdata/<题号>/<序号>.in|.ans`；库里 `testcases` 只存**序号 / 相对路径 / 字节数**
- 理由（需求文档 `OJ-TST-01`）：用例数据量大时不宜存入数据库文本字段
- 路径存**相对路径**（`1/1.in`），换服务器/换目录时库不用改
- 白赚的好处：判题器**只读**那个目录 → 两个工人同时判同一道题也不冲突

### 11. 换一道题 = 换一个目录（判题器不知道自己哪道题）

- `judge.cpp` 只认 `argv[2]` 目录里的 `N.in`/`N.ans`，探测不到 `N.ans` 就停——**它没有「题目」这个概念**
- 实测：同一份源码，`judge .../testdata` 和 `judge .../testdata/1` **都输出 `all 3 test passed`**
- **所以做题库，判题器一行都不用改**——改的是「我们告诉它去哪找」

### 12. 题号必须跟着任务一起排队

- `/submit`（处理请求）**知道**题号；`worker`（后台线程）**不知道**——两个不同的东西，**中间只有队列一条通道**
- 所以 `job_queue.put((job_id, work_dir, problem_id))`，工人 `job_id, work_dir, problem_id = job_queue.get()`
- 类比：前台接单、后厨做菜，**单子上不写桌号，后厨就不知道该送哪**

### 13. 改动顺序：表 → db.py → app.py，中间网站必然坏

- 表改完是**安静的**（没有代码碰它）；`db.py` 一改，**接缝立刻裂**
- 实测的两次报错，**都不在表里、不在 `db.py` 里，长在两边的接缝上**：

```
TypeError: insert_job() missing 1 required positional argument: 'problem_id'
ValueError: too many values to unpack (expected 4)
```

- **总有一边要先动，中间必然有一段对不上**。区别只是「裂多久」——所以永远挑**裂得最短**的路径：先改「没人用」的，最后改「接缝」

### 14. `LEFT JOIN` 不是 `INNER JOIN`（会静默丢行）

- 提交记录要带出题目标题，就得 JOIN；**老提交的 `problem_id` 是 `NULL`，配不上题**
- 实测（同一份数据）：

```
表里实际条数   INNER_JOIN 能查出来   LEFT_JOIN 能查出来
     10                1                   10
```

- **写成 `INNER JOIN`，9 条历史提交会凭空消失**——不报错，**安安静静少给你 9 行**
- `LEFT JOIN` 保证**左边（`FROM` 后面那张表）的每一行都出现**，配不上的右边填 `NULL`
- 跟「`SELECT *` 导致列顺序静默错位」是同一类毛病：**不报错，但数据不对**

### 15. `NULL` 的语义要单一

- `submissions.username = NULL` 曾经**混了两种含义**：老数据是「当时表里还没这一列」，新数据是「当时没人登录」——一个 `NULL` 表示两件事
- 后来「**登录才能提交**」上线后，未登录根本交不了 → 这个 `NULL` **只可能**是历史数据，问题自动消失
- **教训**：修 bug 有时候不是去修它，是让它不可能发生
- 同理 `problem_id IS NULL` 现在也只表示「这一列引入之前的老数据」

### 16. 输出一律转义（防 XSS）

- **病**：用户填的内容混进了 HTML，**被浏览器当成命令执行**（跟 SQL 注入是同一个病，只是发病地方不同）

| | XSS | SQL 注入 |
| --- | --- | --- |
| 病 | 数据混进 **HTML** | 数据混进 **SQL** |
| 谁分不清 | 浏览器分不清哪个是标签 | 数据库分不清哪个是语句 |
| 药 | **转义**：`<` → `&lt;` | **参数化**：`%s` 占位符，值和语句分开送 |

- **规矩**：**凡是不是你亲手写的字面量，一律转义**，不逐个判断「这个安不安全」——省得漏
- 涉及的地方：`nav()`（全站 8 个页面都调它）/ `/whoami` / `/submissions` 循环里五个格子 / `/result` 的 `<pre>`
- ⚠️ **`/result` 那条最隐蔽**：用户提交**编译不过**的代码时，g++ 会把**源码那一行原文**抄进错误信息，判题器输出再被塞进 `<pre>`
  - 实测复现：提交 `int main(){ int <b>X</b>; return 0; }` → `/result` 页面里出现**三个未转义的 `<b>X</b>`**
  - 路径绕了四道手：**源码 → g++ 报错 → 判题器输出 → 数据库 → 页面**，所以平时想不到
- ⚠️ Python 的坑：`escape()` 返回的是 `Markup`（带「我已安全」标记的字符串），**它和普通字符串用 `+` 拼，会反过来把普通字符串也转义掉**——页面上会显示出 `&lt;h3&gt;` 这样的字面量。**改用 f-string 插值**（`f"<td>{escape(x)}</td>"`）就没这个问题

### 17. 让非法状态根本产生不了（新建的题必是草稿）

- 规则是「题目必须先有至少一个测试点才能发布」。比**检查**更省事的做法是**让它没法发生**：
- 新建时 `create_problem()` 把 `is_published` 写死成 `0`，表单上**干脆不放**「发布」勾选框。刚建的题一定没有测试点，那它就不可能以「已发布」的状态出生
- 发布只可能发生在编辑页，那里再校验一次
- **校验用哪份数据很重要**：判「有没有测试点」用的是**本次提交上来的**测试点，而这份数据紧接着就落盘了 —— 校验和落盘在同一次请求里，中间没有别人插手的余地
  - 要是拆成「测试点管理」和「发布开关」两个页面、两次请求，就会出现：管理员 A 检查时看到 3 组 → 管理员 B 把 3 组删了 → 管理员 A 的发布请求才落地
  - 这类「检查完了、用之前，东西被改了」的毛病叫 **TOCTOU**（time-of-check to time-of-use），是并发里的常客
- 跟 §15「修 bug 有时候不是去修它，是让它不可能发生」是同一个手法

### 18. 「删除」的另一半是「清理」

- 需求点名了一个坑：删掉中间某一组测试点后**必须重编号**，否则判题器在号跳掉的地方停住，后面的测试点永远跑不到
- 但重编号只解决了一半 —— **光「把新的前 N 组写进去」是不够的**：
  - 原来 3 组，删掉中间一组变成 2 组。只写 `1.in` / `2.in`，磁盘上那个旧的 `3.in` **还在原地站着**
  - 判题器恰恰是靠「探测下一个 `.ans` 存在不存在」来决定还有没有数据的，于是它会把这**陈年的 3.in 当成「还有下一组」**，拿过期数据接着判
- 所以 `save_testcases_to_disk()` 的做法是：**先把 `testdata/<题号>/` 整个目录删掉，再从头写**
- 实测（3 组 → 删掉中间那组）：

```
删之前磁盘：  1.ans 1.in 2.ans 2.in 3.ans 3.in
删之后磁盘：  1.ans 1.in 2.ans 2.in          ← 3.* 确实消失了
2.in 的内容： -5 5                          ← 正是原来第 3 组的内容
重新提交：    all 2 test passed             ← 判题器手里确实只有 2 组
```

- **证据是最后那行**：残留没清掉的话，判题器会报 `all 3 test passed` —— 一份「成功」的报告，底下藏着一组过期数据。这是「不报错、但结果不对」家族的又一员（同族：§14 的 `INNER JOIN` 静默丢行、§16 的 XSS）

### 19. 库和磁盘都要写：先落盘，再记账

- 测试点存两处：**内容在磁盘**（`testdata/<题号>/`），**元信息在库**（`testcases` 表）。一次保存要动两处，而**两处不可能同时成功**
- 中途断掉（磁盘满、进程被杀、库连接超时）一定会留下不一致 —— 问题不是「怎么避免不一致」，是「**要哪一种不一致**」：

| 顺序 | 断在中间会怎样 | 后果 |
| --- | --- | --- |
| 先改库、后落盘 | 库里记着 5 组，判题器手里只有 3 组 | 页面骗人，**判题结果是错的** |
| **先落盘、后改库** | 磁盘有 5 组，账本只记了 3 组 | 判题**是对的**，只是「共 N 个测试点」的数字偏小 |

- 判题器只认磁盘：**磁盘是真相，库是账本**。账本记错可以日后对账补上；真相错了就是判错
- 两边都可能不一致的时候，挑**错得轻**的那边

### 20. `DELETE` + `INSERT` 要裹在一个事务里

- 「整份替换」测试点的写法是：先 `DELETE` 掉这道题的全部行，再按序 `INSERT`
- 这两步得同生共死。**不裹事务**的话：`DELETE` 执行完、`INSERT` 挂了 → 元信息**清空**、新的**一条没写**，这道题的测试点在库里整个消失
- 做法：这条连接默认不自动提交，中间不 `commit`，最后才 `commit()`。中途抛异常 → 连接关掉时回滚 → **原来的元信息一条没少**
- 顺带两层保险：`UNIQUE (problem_id, ordinal)` 由数据库兜底（§8），重编号是我们自己排的 —— **排错了数据库会当场拒绝**，这是好事

### 21. GET 是「安全」的，删除就得走 POST

- HTTP 里 GET 的约定是**安全**（不产生副作用）+ **幂等**。浏览器会**预取**链接、爬虫会顺着页面上的链接爬、`<img>` 标签也能悄悄发一次 GET
- 删除做成一个 `<a href="/admin/problem/1/delete">` 的话，**谁的爬虫扫一遍你的站，题就没了**
- 所以写操作一律 `<form method="POST">` + 按钮，不当链接用
- 实测：`GET /admin/problem/1/delete` 返回 **405**（这个路径只收 POST），不是 200

### 22. 存完就跳走（PRG）

- 保存成功后 `return redirect(...)`，而不是直接渲染结果页
- 原因：**浏览器把「刷新」理解成「把刚才那个请求再发一遍」**。直接渲染的话，管理员存完按一下 F5，表单再交一次 —— 库里多出一道一模一样的题
- 跳转之后地址栏是一个普通 GET，F5 只是重新看一眼列表，什么都不会发生
- 这个模式叫 **Post/Redirect/Get**
- ⭐ **写这轮笔记时才发现，`/submit` 原来也踩了这个坑**：它的 POST 直接渲染结果页（返回 200），地址栏就停在 POST 上 —— 实测「同一个请求发两次」，提交记录 **0 → 2**，还白判一次题（2 核的机器上会拖慢所有人排队）。已改成 `redirect(f"/result/{job_id}")`（`2e71dd2`）。修后重测：交一次回 **302** → 模拟 F5 重发那个 GET → **记录数一次都没多**
- **这个坑自己测试时看不出来** —— 点了保存、看到成功就关了，谁会在成功页面上按 F5？但用户真的会

### 23. 浏览器交上来的换行是 CRLF

- HTTP 表单提交的多行文本，换行在传输中规定是 `\r\n`。所以「从管理页配出来的测试点」天生带 `\r`
- 而判题器比对答案是**逐行 `getline` 读、行尾补一个 `\n`、再拼成整串比**。文件里是 `5\r\n`，拼出来就是 `"5\r\n"`；选手程序在 Linux 上用 `cout` 输出的是 `"5\n"` —— **差一个看不见的 `\r`，字符串就是不相等**
- 落盘前一律 `text.replace("\r\n", "\n")`
- **实测反证**（同一份正确代码，只动答案文件的行尾）：

```
1.ans 是  "30\n"    →  Test 1 AC  Test 2 AC  Test 3 AC   all 3 test passed
1.ans 改成 "30\r\n"  →  Test 1 WA  （立刻停止）
```

- 这种反证习惯值得养成：**光证明「改完之后没问题」不够，得证明「不改就真有问题」** —— 否则你分不清是修好了，还是本来就没病
- 白赚的好处：判题器是「按行比」，所以答案文件最后**多一个或少一个换行都不影响结果**

### 24. 一条约束可以「不用检查」—— 如果它是另一条规则的推论

- 需求 `OJ-SYS-01` 写着：「系统中**至少保留一个可用管理员账号**」
- 直觉反应是写个检查：降权/禁用之前数一下还剩几个管理员，最后一个就拦住
- **其实不需要。** 因为还有另一条更简单的规则：**管理员不能对自己操作**
- 推论：要降权/禁用**某个**管理员，**必须由另一个管理员来点** —— 那一刻场上**至少有两个**活跃管理员，弄完还剩一个。**「至少保留一个」是这个推论的必然结果，不是一条独立规则**
- 所以真正的保证就是**「不能对自己操作」这一句**，它顺手挡掉了「管理员把自己锁死」的一整类事故
- 代码里另外留了一道 `count_active_admins() <= 1` 的检查，按现有路径**触发不了**（操作者自己就是活跃管理员，又不能动自己；所以只要目标是活跃管理员，场上至少 2 个）。**留着的理由是兜底**，注释里诚实写了「它触发不了」
- **要点**：**先找已经成立的简单规则，看新需求是不是它的推论** —— 是的话就别再写一遍。多一条检查，就多一处将来会忘记同步的地方

### 25. 越权判断只要一个字段；「禁用」不是「删除」

- **越权**（`FIX-11`）不需要新表、新字段：`submissions.username` 一直在那儿，它本来就是「这条是谁交的」。**把它当"归属人"读**，一句 `if owner != me and not is_admin(me)` 就够了 —— 数据早就够用，缺的是**有没有想到去用**
- 老数据的 `username` 是 `NULL` → 配不上任何人 → **只有管理员看得到**。这个行为正好是对的，不用特判
- **禁用用户**（`OJ-SYS-01`）用的是 `is_disabled = 1`，不是删行 —— 需求原文就写着「禁用账号后该用户不能登录，但**其历史提交记录保留**」。**跟 §7 的题目软删除是同一个道理**：删人就等于让他所有提交变成孤儿
- ⚠️ **路由参数用 `user_id`，不用用户名**：用户名可能含空格等字符，塞进 URL 要额外编码，数字主键没这个问题

### 26. 这次的部署**没有坏窗口**（对比 §13）

- 这次同时要改表（加 `users.is_disabled`）和改代码，按理又是一次「接缝裂开」
- 但实际顺序是 **① `git pull` ② 跑 `ALTER TABLE` ③ 重启**，中间**网站一直正常**
- 为什么：**`pull` 只改磁盘上的 `.py` 文件，运行中的 Flask 进程内存里还是旧代码** —— 而旧代码**不需要**这一列，所以它继续跑得好好的。等库准备好了，重启用新代码，一次就位
- **规则**：迁移要挑「**旧代码不需要、新代码需要**」的那种先后 —— **先让库超前于代码，再换代码**
- 反过来（先重启后迁移）立刻裂：新代码 `SELECT is_disabled`，而库还没这一列 → 500

### 27. 让判题器「报告结论」，而不是让 Web 层去猜

- 判题器原来打的是 `Test 1` / `run done` / `AC` / `all 3 test passed` —— 那是**给人看的**
- Web 层想知道「这次过了没有」，只能去 `LIKE '%all 3 test passed%'` —— **拿散文当接口**。判题器哪天改一个字的输出，这边就**静默失效**
- 现在判题器最后固定打一行 **`VERDICT: AC`**（取值 `AC/WA/TLE/MLE/RE/CE/NO_DATA`），Web 层按行取
- **顺带一次语义升级**：`run_one_test()` 的返回类型从 `bool` 变成 `string` —— 从「**过没过**」升级到「**为什么**」。`bool` 只够回答前一个问题
- ⚠️ 升级时最容易漏的地方：**TLE 和 RE 原来共用一个 `return false`**。改成字符串时必须**拆成两个 return**，否则会出现「打出 `Time Limit Exceeded`、却返回 `"RE"`」——**打印的和实际的互相矛盾**，而且**编译器完全不管这种事**
- **耗时**：判题器原来**根本没测过时间**（只报 `peak memory`）。用 `clock_gettime(CLOCK_MONOTONIC)` 在 `wait4` 前后各取一次。
  **为什么不用 `CLOCK_REALTIME`**：那是"墙上时钟"，系统时间被改（NTP 校时、手动改时间）它会**跳**，测出来的差可能是负的。`CLOCK_MONOTONIC` 只往前走，专门用来量时间间隔

### 28. 缓存坏了，页面不能跟着坏

- 需求 `OJ-RNK-01` 原话：「异常流程：缓存不可用 → **降级为直接查询数据库，不得因缓存故障导致页面不可用**」
- 做法：**每一次 Redis 调用都单独包 `try/except`** —— 读失败就当没有缓存、去查库；写失败也无所谓，照样返回
- **关键是别把整个函数包一个 try** —— 那样 Redis 一挂函数就抛出去，页面直接 500。**缓存是拿来加速的，它不该有「让服务不可用」的能力**
- 实测：

```
正常                 →  页面标注「Redis 缓存」
systemctl stop redis →  redis-cli: Connection refused
                        GET /rank 仍然 HTTP 200，数据正常，标注「直接查数据库」
重新 start           →  自动回到「Redis 缓存」
```

### 29. 两个「文件改了，可东西没变」的时刻

**① 改了 `.cpp`，但没重新编译**

```
judge      15:20:11
judge.cpp  15:21:34     ← 源码比二进制还晚
```

跑出来还是旧行为（`VERDICT: RE`），**看着像代码没改对，其实跑的是旧二进制**。
Python 改完文件就是新的（只要重启进程）；**C/C++ 改完源码，二进制一个字都不会变** —— 这是编译型语言独有的坑。
**`ls -l` 看时间戳**是最快的判断法：**先看身外之物，再怀疑逻辑**。

**② `ALTER TABLE ADD COLUMN` 默认往最后一列加**

迁移跑完，`verdict` 那几列出现在 `created_at` **之后** —— 而 `schema.sql` 里我写在 `created_at` **之前**。

于是「新库」（照 `schema.sql` 建的）和「老库」（迁移出来的）**列顺序不一样**。功能上没事（我们从不写 `SELECT *`），但这是**埋着的雷**：哪天有人写了 `SELECT *` 再按位置解包（`for a, b, c in rows`），就会**静默错位**。

**修法**：把 `schema.sql` 改成跟实际库一致。**建表脚本和迁移脚本要长成同一个样子**，否则新库老库会慢慢分家。

## 已知问题 / 欠账

- **`FIX-21`：丢失更新**。编辑页是「整份替换」语义，两个管理员同时改同一道题，**后提交的会静默覆盖先提交的**（题面、测试点都算），被覆盖的人完全不知情。注意跟 §17 的 TOCTOU 不是一回事：TOCTOU 是**一个人**「检查完、动手前」被改；这条是**两个人**各写各的。常见解法是 `version` 字段做乐观锁
- **`/admin/problems` 列表页是 N+1 查询**：每行列一次 `count_testcases()`，10 道题就是 11 条 SQL。数据量小无所谓，正经做法是一个 `GROUP BY` 一次带出来
- **`/submissions` 有 `LIMIT 100` 但没做真正的分页**（那只是硬上限）；`created_at` 只有秒精度，同一秒内排序不稳定（`FIX-16`）
- **结果页刷新是「一请求一线程」**，线程数随等待人数线性涨——上生产要换 gunicorn 或改推送
- **`judge_queue` 是进程内队列**：Flask 一重启，排队中和正在判的任务就卡住不动（记录还在，靠 60 秒超时兜底露出来）。跨进程/多判题机要用 Redis
